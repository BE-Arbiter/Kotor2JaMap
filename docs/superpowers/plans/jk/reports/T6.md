## Decisions (ambiguites tranchees)

1. **Pivot** : mesure sur les donnees, pas pris dans les specs. Sur 1 207 couples parent / enfant, l'origine de l'enfant tombe dans la boite du maillage parent (distance moyenne relative 0,014) si on compare
   `pos - pivot_parent` aux sommets bruts ; 0,198 sans pivot, 0,461 avec le signe oppose. Donc sommet dans le repere du noeud = `v + pivot`, rotation autour de l'origine du noeud.
2. **Matrices** : `M = R(pyr) * T(pos) * M_parent` (vecteurs ligne). `R` = roll (Y), pitch (X), yaw (Z), sens trigonometrique, memes angles que les things du .jkl. `NodeMatrices` ne contient pas le pivot ;
   le convertisseur l'ajoute aux sommets.
3. **Orientation / repere** : le MD3 reste dans le repere JK (Z haut, +Y vers l'avant, sens des faces antihoraire confirme sur 25 619 faces sur 25 625). Aucune rotation d'axe ici : l'entite (T7) devra
   convertir le lacet (le 0 de JK est +Y, celui de JA +X).
4. **UV** : `(u / largeur, 1 - v / hauteur)` de la cellule 0 du materiau, comme le niveau (T4). Les valeurs hors 0..1 sont gardees (repetition). Materiau absent de `mats` : 64 x 64 et `TEXTURE_MISSING`
   (la surface est gardee, texture de remplacement).
5. **Faces** : seules les faces `geo >= 3` sont dessinees (`JK_MODEL_FACES_HIDDEN` en avertissement avec le compte pour les autres). Polygones triangules en eventail. Double face (`type & 1`) : triangles
   et sommets dupliques a l'envers (normale inversee). Faces translucides (`type & 2`) : non traitees (voir preoccupations). Normales : normale de sommet si l'eclairage est gouraud (`light >= 3`), sinon normale de face
   (sommets non partages entre faces). Une partie MD3 par materiau, nom de texture = nom du `.mat` sans extension en minuscules, shader `models/jk/<texture>`.
6. **Geoset 0 seul** ; les maillages que aucun noeud ne reference ne sont pas dessines (comme le moteur ; un seul cas, `kd.3do`).
7. **Echelle** : sommet = `v * MetresPerJkUnit (8,6) * scale` avec `scale` = unites JA par metre (40). Plafond ±511 comme `PlaceableConverter` : si le plus grand |coordonnee| (toutes les images ecrites)
   depasse 511, division par `k = ceil(max / 511)` et `JkMd3.ModelScale = k` (valeur de la cle `modelscale` de l'entite). Hors echelle par defaut : `models/jk/s<echelle>/` comme `ModelDirectory` de KOTOR.
   24 des 477 modeles passent par la division (taille 8,6 m par unite JK).
8. **`Min` / `Max`** : metres de la scene (unites JK x 8,6), repere du modele, union de toutes les images (pas des unites JA). `Fps` : celui de l'animation, 0 sans animation.
9. **Animation** : le noeud du modele est apparie a la piste par nom (insensible a la casse), sinon par indice si les nombres de noeuds sont egaux, sinon pose de repos (`JK_KEY_NODE_UNMATCHED`). Position cle et angles
   cle sont absolus (remplacent la pose de repos). Interpolation lineaire de la position ; angles lineaires par le plus court chemin, avec le nombre de tours impose par la variation par image de l'entree
   (verifie : variation x ecart d'images = difference des entrees). Avant la premiere cle / apres la derniere : pose maintenue. Nombre d'images = `FRAMES` (au plus 1024, `JK_KEY_TRUNCATED` au-dela ; plus long cas
   des donnees : 411). Animation sans aucun mouvement : une image.
10. **Rotation pure** : un seul noeud change de pose, sa position est constante, et l'increment de rotation entre images consecutives (calcule en quaternion, `R_f^-1 * R_f+1`) garde le meme axe (a 1,8 degre pres) et le meme
    angle (a 3 % pres) sur toute l'animation. Axe donne dans le repere du modele (par la matrice du parent au repos), `DegreesPerSecond` = angle par image x fps, signe = sens trigonometrique autour de l'axe,
    `RotationCenter` = origine du noeud (le `func_rotating` tourne autour de l'origine de l'entite : T10 devra poser l'entite sur ce centre). Dans ce cas le MD3 n'ecrit qu'une image (`Frames` = 1) et `Min`/`Max`
    couvrent quand meme toute la rotation echantillonnee. Plusieurs noeuds qui tournent de concert (rotors a plusieurs pieces) ne sont pas consideres comme pure rotation : MD3 a images multiples.
11. **Echecs** : modele absent `JK_MODEL_MISSING`, illisible `JK_MODEL_UNREADABLE`, sans face dessinable `JK_MODEL_EMPTY`, MD3 refuse (plus de 64 surfaces, shader trop long...) `JK_MODEL_MD3_FAILED` ; animation
    absente / illisible `JK_KEY_MISSING` / `JK_KEY_UNREADABLE` (le modele est alors converti sans animation). Aucune exception ne sort pour des donnees de jeu.

## Preoccupations

1. **Aucune rotation pure dans les `.key` reels** (3 321 couples modele / animation essayes, 0 detecte). Le code est teste sur donnees synthetiques ; les objets qui tournent dans les niveaux le font sans doute par
   vitesse angulaire de gabarit ou par COG (T9 / T10 a confirmer). Le sens de `DegreesPerSecond` par rapport au `func_rotating` de JA (signe, axe) reste a verifier en jeu.
2. **`sphere.3do` n'est pas convertible** : ses 196 faces sont en mode « points ». Si un gabarit l'utilise visiblement, il faudra un traitement (T7) ; le convertisseur renvoie null avec `JK_MODEL_EMPTY`.
3. **Translucide** : les faces `type & 2` sont ecrites opaques ; la transparence des modeles dependra du shader `models/jk/<texture>` (a la charge de l'appelant avec `JkMaterial.HasTransparency`). Les
   textures ne sont pas exportees ici : la liste est dans `Md3Asset.Textures`.
4. **`INSERT OFFSET` ignore** (non verifie : il est probablement propre a l'editeur) ; a revoir si des objets flottent / s'enfoncent en jeu.
5. **Taille** : un personnage anime (`tk.3do` + `tkidle.key`, 283 images) donne un MD3 d'environ 1 Mo ; sans consequence tant que les acteurs ne sont pas places, mais le budget pk3 est a surveiller pour les objets animes.
6. Un modele a plus de 64 surfaces (hors limite de `Write`) echoue en `JK_MODEL_MD3_FAILED` plutot que d'etre reparti sur plusieurs fichiers : aucun cas parmi les 476 modeles convertibles, mais `WriteSplit` n'a pas
   d'equivalent a images multiples.
