# T3 - Catalogue des zones SWTOR (id -> nom lisible)

## Ce qui a ete fait
- `src/Swtor.Core/Gom/` : lecteur GOM **copie** de SWTOR-Character-maker (`GomNodes`, `GomObject`, `GomObjectReader`, `GomReader`, `GomDatabase` sans schema), en-tete "Copied from ...", pas de ProjectReference.
- `AreaDat.InternalName` : nom interne lu dans le dernier bloc d'`area.dat` (`AreaDatReader.ScanInternalName`).
- `src/Swtor.Core/Areas/SwtorAreaNames.cs` : lecture des noms dans le GOM (`mapAreasDataProto`, `world.areas.<id>.mapdata`), `StringResolver` (tables .stb d'une langue, `fr-fr` par defaut, repli `en-us`), choix du nom parmi les pages de carte.
- `src/Swtor.Core/Areas/SwtorAreaCatalog.cs` : `SwtorAreaEntry` {Id, InternalName, DisplayName, NameSource, Category, Planet, ArtFolder, RoomCount, AssetCount, ModelAssetCount, RoomBytes, MapPages, Minimaps}, `Build`, `Load` (cache JSON `swtor_areas.json` dans le workDir, reconstruit s'il manque, si la version / la racine / la langue / le nombre de dossiers de zone change, ou avec `rebuild`), `Find(id | nom interne)`, `Filter`, `CountModels` (compte exact des instances de modele, lit les rooms).
- CLI `swtor-list-areas [--assets racine] [--filter texte] [--rebuild] [--models] [--work dossier] [--config fichier] [--language fr-fr]` (`SwtorListAreasCommand`) ; `swtor-dump-area` accepte maintenant un nom interne (`war_planworking`) en plus de l'id ou du dossier. Cache par defaut : `<workDir de la config>\swtor_areas.json` (donc `C:\jka_maps\kotor_work\swtor_areas.json`).
- Spec : section "Noms des zones" ajoutee a `docs/superpowers/specs/swtor-formats.md`.

Resultat final : `NameSource` = gom 226, gom-map 11, internal 30, id 0. Soit 237 / 267 (88,8 %) avec un vrai nom localise. Les noms sont en **francais** (seul `fr-fr` est extrait ; `gamedata/str` ne contient que `stb.manifest`).

Faits utiles :
- Les identifiants de chaine ne disent pas leur table : `sys/worldmap.stb` en resout 172, `gui/map.stb` 18, `spvp/misc.stb` 4, `rdd.stb` 3 ; `StringResolver` les essaie dans cet ordre puis les autres tables de la racine, `sys`, `gui`, `spvp`.
- Le nom donne par le GOM est celui de la **zone** : plusieurs zones portent le meme nom (Balmorra x2, Taris x2, Voss x3, "Chantiers navals perdus" pour les 3 `spvp_001*`, `Defenseur` pour les deux vaisseaux Jedi...). Le champ `InternalName` / l'id les distinguent.
- Temps : reconstruction (ouverture du GOM, 726 494 objets, + 267 `area.dat`) environ **6 a 8 s**, relecture du cache JSON (108 Ko) **< 100 ms** ; `swtor-list-areas` avec cache environ 0,7 s (demarrage du processus compris).
- Memoire : l'ouverture du GOM garde les entetes des 726 494 objets (plusieurs centaines de Mo) le temps de la construction uniquement.

## Inconnus et limites
- Le lien **room -> page de carte** (nom de lieu par room, ex. « Cantina de Varath ») n'est pas fait : les pages portent un nom `map_*` qui ressemble au nom de fichier de minimap, pas au nom de room. A creuser si on veut lister les lieux a l'interieur d'une grande zone.
- La liste d'ordre de resolution des tables de chaines est empirique (on ne sait pas quelle table contient un id) ; 7 ids de zones restent sans texte (`lobby`, `spacecombat9`...).
- Les champs du GOM sont des hachages : les ids `0x400000080027BF7F` (texte), `0x400000085CD72A38` (cle de chat), `0x40000005B5F9C772` (pages), etc. ont ete identifies par leurs valeurs et sont codes en dur dans `SwtorAreaNames` ; une mise a jour du jeu qui change les hachages ne casse que la partie nom (repli sur le nom interne).
- La categorie est heuristique ; le nom interne est lu par une heuristique de bloc final (verifie sur 267 / 267, plausible partout).
